# Custyard Code Audit, 2026-09-28

**34 verified findings (7 high, 14 medium, 13 low). Fix these first: the operator magic-link endpoint is effectively not rate-limited, and the limiter's ETS table does not persist between connections. Turning on IMAP crash-loops the app at boot, LMTP transaction state leaks between messages on one connection, and the locked Bandit 1.12.0 has published CVEs.**

- **Scope:** `custyard/custyard` at `8b01f66`. The audit covered five dimensions: Security, Correctness, Test coverage, Dead code and Dependency risk.
- **Verification:** Each finding was adversarially checked by three independent verifiers. The consensus is listed with each finding.
- **Duplicates:** Two issues were reported under both Security and Correctness. They are kept in both sections and cross-referenced, so the 34 findings cover 32 distinct issues:
  - the unbudgeted magic-link endpoint (S-1 / C-1)
  - the Slack missing-signature crash (S-3 / C-9)
- **Paths:** All paths are relative to the repository root.

### Suggested order of work

1. **Fix operator login throttling (S-1/C-1, C-2).**
   - Count every `POST /operator/login` toward the limit.
   - Give the limiter a table owned by a long-lived process. Reusing `Custyard.RateLimit` covers this.
   - Add a cooldown per email address.
2. **Fix the boot and delivery bugs (C-3, C-4).**
   - IMAP poller: wire in `organization_id`.
   - LMTP: reset the transaction state after each DATA.
3. **Upgrade Bandit to 1.12.5 or later (D-1).** Only the lockfile changes. Also add `mix hex.audit` and `mix deps.audit` to CI (D-2) so this does not happen again.
4. **Add tests for the operator auth flow (T-1, T-2).** Do this together with the fixes above, so the fixes are covered by tests.
5. **Fix the rest in any order.** This covers the 500s and misclassified MTA replies: C-5 through C-9 and S-2. After that, the remaining test gaps, dead code and the license question (D-3).

## Security

### S-1 · HIGH · The magic-link request endpoint is effectively not rate-limited, so an attacker can keep invalidating an operator's login link

- **Location:** `lib/custyard_web/controllers/operator/session_controller.ex:37`
- **Category:** broken-authn / rate-limiting
- **Consensus:** 3/3 verifiers
- **Duplicate of:** C-1

**Why it matters:**

- `SessionController.create` always ends in a 302 redirect to `/operator/login/sent`, for known and unknown emails alike.
- `CustyardWeb.Plugs.LoginRateLimit` (`lib/custyard_web/plugs/login_rate_limit.ex:97-103`) only records an attempt when the response is not a 3xx. No `POST /operator/login` therefore ever counts toward the 5-per-minute budget, and the plug never returns 429 for this action.
- `create/2` also always calls `OperatorAccount.login_token_changeset/1` and `Repo.update!` (lines 24-27), which overwrite `login_token` and `login_token_expires_at` on every request.

An anonymous attacker who knows an operator's email can therefore:

- send unlimited magic-link emails through the mail provider. This is mail bombing, and it costs money and sender reputation.
- keep regenerating the token, so the operator's link is already invalid when they click it. Magic links are the app's only login method, so this locks the operator out.

**Suggested fix:**

- Count every `POST /operator/login` toward the limit, whatever the response status. Either record the attempt in `call/2` before dispatch, or count 3xx responses for `:create`.
- Add a cooldown per email address. Either do not issue a new token while the current one is valid for more than N minutes, or keep the current token and resend it.
- Consider keying the limit on both the IP and the normalized email.

### S-2 · LOW · Magic-link verification is a GET that changes state: it consumes the token and starts an operator session

- **Location:** `lib/custyard_web/controllers/operator/session_controller.ex:61`
- **Category:** session-handling
- **Consensus:** 3/3 verifiers

**Why it matters:**

- The first hit on `GET /operator/login/verify/:token` clears the single-use token and puts `operator_id` into the session.
- Corporate mail-security scanners and email clients that prefetch links routinely GET the links in incoming mail. When one does:
  - the token is used up, and the operator then sees "expired".
  - the scanner's HTTP client receives a valid operator session cookie.
- The repo already handles this problem for `/claim/:token`: `ClaimConfirmationController` uses a peek-then-POST pattern. The operator login grants more privilege and does not.

**Suggested fix:** Mirror `ClaimConfirmationController`.

- On GET, check that the token is well-formed and exists, without consuming it. Render a page with a CSRF-protected "Log in" button that POSTs to `/operator/login/verify/:token`.
- Only the POST clears the token and creates the session.

### S-3 · LOW · Slack `verify_request/4` crashes with a 500 when the `X-Slack-Signature` header is missing, instead of returning 401

- **Location:** `lib/custyard/webhooks/adapters/slack.ex:45`
- **Category:** input-validation
- **Consensus:** 3/3 verifiers
- **Duplicate of:** C-9

**Why it matters:**

- For `:slack`, `WebhookController.verify_with_secret/3` (`lib/custyard_web/controllers/webhook_controller.ex:181-183`) passes on the result of `get_signature_header/2`. That result is `nil` when the header is missing.
- `Slack.verify_request/4` has no clause for `nil`. It calls `String.downcase(nil)` and raises `FunctionClauseError`.
- The Lettermint, Zendesk and Intercom adapters each have an explicit `verify_signature(_payload, nil, _secret)` clause.

As a result, an unauthenticated caller who knows a `callback_token` can trigger 500s and Sentry events at will on Slack routes. The endpoint is documented to return a generic 401 in this case.

**Suggested fix:**

- Add a clause for the missing header ahead of the main clause:

  ```elixir
  def verify_request(_raw_body, _timestamp, nil, _secret), do: {:error, "missing signature header"}
  ```

- Guard the main clause with `when is_binary(signature)`.

## Correctness

### C-1 · HIGH · The login rate limiter never counts magic-link requests, because `create/2` always redirects

- **Location:** `lib/custyard_web/controllers/operator/session_controller.ex:42`
- **Category:** logic-error
- **Consensus:** 3/3 verifiers
- **Duplicate of:** S-1

**Why it matters:**

- `LoginRateLimit` only records an attempt when the response is not a 3xx (`record_failed_attempt`, `login_rate_limit.ex:101`).
- For any non-empty email, `create/2` redirects to `/operator/login/sent` (Post/Redirect/Get), whether or not the account exists. Only the empty-email clause renders a 200.
- The plug is applied with `when action == :create`, but it never counts a real submission. An unauthenticated client can POST a known operator email in an endless loop.
- Each request:
  - rotates `login_token` via `login_token_changeset/1` and `Repo.update!`, which invalidates the operator's outstanding link. The operator cannot log in.
  - sends a new email, so the endpoint can be used for email bombing.
- The comment on lines 39-40 shows the author treated redirects as successes. In a magic-link flow every POST is a request and has to count against the budget.

**Suggested fix:**

- Count every `POST /operator/login` toward the limit. Either drop the status check in `record_failed_attempt`, or add a `count_all: true` option for `:create`.
- Add a second bucket keyed on the normalized email, so requests from many IPs cannot flood a single operator address.
- Alternatively, use `Custyard.RateLimit` with a dedicated `:operator_login` bucket. It already counts every event.

### C-2 · HIGH · The login rate-limit ETS table is owned by a short-lived request process, so it is deleted when that connection closes

- **Location:** `lib/custyard_web/plugs/login_rate_limit.ex:116`
- **Category:** concurrency
- **Consensus:** 3/3 verifiers

**Why it matters:**

- `ensure_table_exists/0` runs from `call/2`. It also runs from `init/1` when the router is built, and the compiler process that owns the table at that point exits.
- `:ets.new/2` makes the calling process the table's owner. In `call/2` that is the Bandit connection process serving the current request.
- When that connection closes, the table is deleted, along with every recorded attempt for every IP. The next request silently creates a new, empty table.
- An attacker can reset the limiter whenever they want: open a connection, make the first request after a gap, and close it. In normal traffic the recorded attempts rarely last long enough to limit anything.
- Other code in the repo gets this right:
  - `Custyard.RateLimit` owns its table in a GenServer.
  - `LMTPServer.ensure_rate_limit_table/0` creates its table in `start_link`, under the supervisor.

**Suggested fix:** Create the table from a process that lives for the whole application run. Either:

- add a small GenServer or Agent to the supervision tree to own `:login_rate_limit` (or set an `heir`), or
- reuse `Custyard.RateLimit` (`RateLimit.check_rate(:operator_login, ip)`) and delete the custom ETS handling.

### C-3 · HIGH · The IMAP poller starts without its required `:organization_id`, so `IMAP_ENABLED=true` crash-loops the app at boot

- **Location:** `lib/custyard/application.ex:213`
- **Category:** correctness
- **Consensus:** 3/3 verifiers

**Why it matters:**

- `Custyard.Email.ImapPoller.init/1` calls `Keyword.fetch!(opts, :organization_id)` (`imap_poller.ex:90`), and message dispatch needs that value to find the inbound route.
- `Application.maybe_add_imap_poller/1` only passes `host`, `port`, `username`, `credential_fetcher`, `folder`, `poll_interval` and `ssl`.
- `config :custyard, :imap` in `config/runtime.exs` has no `organization_id` either.
- In production with `IMAP_ENABLED=true`, this is what happens:
  1. The child raises `KeyError` in `init`.
  2. The `one_for_one` supervisor restarts it until it hits `max_restarts`.
  3. `Custyard.Supervisor` exits, and the release goes down with it.
- The unit tests pass `organization_id` explicitly (`imap_poller_test.exs:28`), so they do not catch the missing wiring.

**Suggested fix:**

- Add `organization_id: parse_int.("IMAP_ORGANIZATION_ID", nil)` to the `:imap` config in `runtime.exs`.
- Pass it through in `maybe_add_imap_poller/1`.
- When it is missing, fail fast at config time with a clear error, or skip the poller and log an error.

### C-4 · HIGH · LMTP session state (`to`, `organization`, `from`, `declared_size`) is never reset after DATA, which breaks connections that carry several messages

- **Location:** `lib/custyard/email/lmtp_server.ex:887`
- **Category:** logic-error
- **Consensus:** 3/3 verifiers

**Why it matters:**

- gen_smtp resets its own envelope after `handle_DATA` but keeps the callback state.
- `process_and_respond/2` returns `%{state | message_count: count + 1}`, and the error branches return `state` unchanged. `state.to`, `state.organization`, `state.from` and `state.declared_size` therefore carry over to the next transaction on the same connection. Only an explicit RSET clears them, via `handle_RSET`.

This has three consequences:

1. **Mail to a second organization bounces.** `handle_RCPT` (line 689) permanently rejects with 550 any recipient whose organization differs from the previous message's. Postfix and other MTAs reuse one LMTP connection for recipients on different domains, so legitimate mail is bounced.
2. **Recipients run out.** `length(state.to)` keeps growing. Once a connection has seen `max_recipients` recipients in total (default 100), every RCPT gets 452.
3. **Size limits misfire.** A leftover `declared_size` can trigger a false 552.

The existing multi-message test (`lmtp_server_test.exs:1051`) only sends to one organization, so it does not catch this.

**Suggested fix:**

- Reset the transaction fields after every DATA outcome, for example:

  ```elixir
  defp reset_transaction(state),
    do: %{state | from: nil, to: [], data: nil, declared_size: nil, organization: nil}
  ```

- Apply it to the state returned from both the `:ok` and `:error` branches of `process_and_respond/2`, and from the early-rejection branches of `handle_DATA/4`.
- Add a test that delivers to two different organizations on one connection.

### C-5 · MEDIUM · Duplicate `message_id` detection is global, so a message can be attached to another organization's conversation and silently dropped

- **Location:** `lib/custyard/webhooks/purposes/sender_matching.ex:180`
- **Category:** correctness
- **Consensus:** 3/3 verifiers

**Why it matters:**

- `find_by_message_id/2` and `ThreadMatcher` are correctly scoped to the organization.
- `Message.insert_idempotent/1` (`message.ex:142`) is not. Its fallback does a global `Repo.get_by(Message, message_id: ...)`, because `messages_message_id_unique_index` is global.

This goes wrong when a Message-ID already exists in a conversation of organization B and a new message arrives through organization A's route. That happens when the same email is delivered to two organizations over LMTP, or a webhook payload replays a known Message-ID. `create_message_with_dedup/3` then sees `message.conversation_id != conversation.id`, deletes the conversation it just created in A, and returns B's conversation. As a result:

- The message is never stored for A, but the caller still gets 250 or 200.
- `broadcast_updates/2` pushes `conversation_updated` onto B's topic.
- The webhook response exposes B's `conversation_id` to whoever called A's route.
- Async purposes then run with a conversation from a different organization than `route_context`.

**Suggested fix:**

- Scope the fallback lookup to the organization: join `conversations` and add `where c.organization_id == ^org_id`.
- Treat a collision that exists only across organizations as a distinct message. Either:
  - make the uniqueness organization-aware (a composite index, or store `message_id` per conversation), or
  - on a cross-organization collision, derive a new `message_id` (for example `<original>+org<id>`) instead of adopting the other organization's conversation.

### C-6 · MEDIUM · Oversized JSON and form bodies return 500 instead of 413, because the body reader returns a tuple `Plug.Parsers` does not recognize

- **Location:** `lib/custyard_web/plugs/cache_raw_body.ex:40`
- **Category:** wrong-error-handling
- **Consensus:** 3/3 verifiers

**Why it matters:**

- `Plug.Parsers.JSON` and `Plug.Parsers.URLENCODED` handle these results from the body reader:
  - `{:ok, body, conn}`
  - `{:more, _, conn}`, which becomes a 413 too-large response
  - `{:error, :timeout}` and `{:error, _}`
- `CacheRawBody.read_body/2` turns `{:more, ...}` into `{:error, :body_too_large, conn}`. That 3-tuple matches none of them.
- As a result, any body over the 1 MB limit raises `FunctionClauseError` in the endpoint. Sentry records a crash instead of a clean `Plug.Parsers.RequestTooLargeError`.
- The unit test (`cache_raw_body_test.exs:33`) asserts the 3-tuple, and its comment assumes Plug translates it. Plug does not.
- The reader is installed for the whole endpoint, so every JSON or form POST is affected, not just webhooks.

**Suggested fix:**

- Return the `{:more, partial, conn}` tuple unchanged; `Plug.Parsers` already maps it to 413. Alternatively, raise `Plug.Parsers.RequestTooLargeError` yourself.
- Update the test to match.

### C-7 · MEDIUM · `extract_email/1` crashes on a nil sender: a missing From becomes a 500 on webhooks and a crashed session on LMTP

- **Location:** `lib/custyard/email/sender_matcher.ex:126`
- **Category:** null-handling
- **Consensus:** 3/3 verifiers

**Why it matters:**

- `Regex.run/2` raises `FunctionClauseError` when `from` is nil.
- `from` can be nil in two ways:
  - `Lettermint.normalize` sets `from: params["from"] || params["sender"]`, which is nil when both are absent.
  - `Parser.parse` returns `from: nil` for a message with no From header, and `EmailAdapter.normalize` passes that through.
- `SenderMatching.resolve_sender` then calls `SenderMatcher.match_within_org(nil, org_id)`, which calls `extract_email(nil)` and raises.
- **Webhook path:** a signed but malformed payload causes an unhandled exception (500 plus a Sentry event) instead of a 4xx.
- **LMTP path:** the exception escapes `handle_DATA` and kills the gen_smtp session process before any SMTP reply is sent.
  - The MTA sees a dropped connection and treats it as a temporary failure.
  - It retries the same message for days, crashing a session on every attempt.

**Suggested fix:**

- Check the sender early, in `SenderMatching.resolve_sender` or in `SenderMatcher.match` / `match_within_org`. Return `{:error, :missing_sender}` when `normalized.from` is nil or blank.
- Map that error to 422 in `WebhookController` and to a permanent 550 in `LMTPServer.process_email/2`.

### C-8 · LOW · The LMTP server reports permanent validation failures to the MTA as a temporary 421, which causes retry loops lasting days

- **Location:** `lib/custyard/email/lmtp_server.ex:1014`
- **Category:** wrong-error-handling
- **Consensus:** 3/3 verifiers

**Why it matters:**

- `process_email/2` maps every unrecognized `{:error, reason}` to `{:error, :temporary, reason}`, which the MTA receives as `421 4.7.0 Temporary failure`.
- `Dispatcher` and `SenderMatching` return `{:error, %Ecto.Changeset{}}` for rejections that will fail the same way on every attempt, such as:
  - an invalid sender address, rejected by `Contact.changeset`
  - a subject or body that is too long
- The MTA keeps requeuing and redelivering the message until its queue lifetime runs out (5 days by default in Postfix). Each attempt repeats the parsing and database work.
- The sender never receives a bounce.

**Suggested fix:**

- Add a clause:

  ```elixir
  {:error, %Ecto.Changeset{} = cs} -> {:error, :permanent, {:validation_failed, cs.errors}}
  ```

- Treat other deterministic errors, such as `{:error, :parse_failed}`, as permanent too.
- Keep `:temporary` for database and connectivity errors.

### C-9 · LOW · Slack `verify_request/4` crashes with `FunctionClauseError` when the `X-Slack-Signature` header is missing

- **Location:** `lib/custyard/webhooks/adapters/slack.ex:45`
- **Category:** null-handling
- **Consensus:** 3/3 verifiers
- **Duplicate of:** S-3

**Why it matters:**

- `WebhookController.verify_with_secret(conn, :slack, secret)` passes `signature = List.first(get_req_header(conn, "x-slack-signature"))`, which is nil when the header is absent.
- `verify_request/4` parses and validates the timestamp first, then calls `String.downcase(nil)` and raises. It never returns `{:error, "missing signature"}`.
- The other adapters guard with `when is_binary(signature)`. Slack does not.
- An unauthenticated request that has only a valid timestamp header therefore produces a 500 and a Sentry event instead of the intended generic 401.

**Suggested fix:** Add `def verify_request(_raw_body, _timestamp, nil, _secret), do: {:error, "missing signature header"}` and a guard against non-binary signatures, both ahead of the main clause.

## Test coverage

### T-1 · HIGH · The magic-link verify flow has no tests at all: expiry, single use, format check and session renewal are all untested

- **Location:** `lib/custyard_web/controllers/operator/session_controller.ex:62`
- **Category:** untested-security-path
- **Consensus:** 3/3 verifiers

**Why it matters:**

- No test file references `SessionController`, and no test hits any `/operator/login*` route. A grep of `test/` for `operator/login`, `login_token` and `verify` finds only the `OperatorAccount` unit tests.
- The operator authentication entry point has no end-to-end tests. `verify/2` is responsible for all of the following, and none of it is checked:

  | Lines | Responsibility |
  |---|---|
  | 63 | Reject a malformed token |
  | 65 | Reject an unknown token |

  | 76-77 | `configure_session(renew: true)` and `put_session(:operator_id)` |

- A token with characters outside `[A-Za-z0-9_-]` and an unknown token both render the generic invalid page, with identical bodies.
- A successful verify changes the session id (renewal) and redirects to `/operator`.

### T-4 · MEDIUM · The LMTP peer IP allowlist (`ip_allowed?/2`) has no tests

- **Location:** `lib/custyard/email/lmtp_server.ex:576`
- **Category:** untested-security-path
- **Consensus:** 2/3 verifiers

**Why it matters:**

- `init/4` (lines 503-523) rejects connections from peers that are not in `:allowed_ips`, using the four `ip_allowed?` clauses at lines 576-596. Those clauses handle:
  - `{ip, port}` tuples as well as bare IP tuples
  - a final fall-through that denies any unexpected format
- A grep of `test/` for `allowed_ips` finds nothing. Every LMTP test runs with the default (`@default_allowed_ips`).
- This is the only connection-level access control on a server that faces the network. A clause-ordering bug could have either effect below, and CI would not notice:
  - the fallback denying every `{ip, port}` peer, which locks out the MTA in production
  - `:any` failing to match, or some other mistake that silently opens the listener

**Suggested fix:**

- In `lmtp_server_test.exs`, start a server with `allowed_ips: [{10,0,0,1}]`. Assert that a loopback client receives the `554 5.7.1` banner, the socket closes, and the telemetry event `[:custyard, :lmtp, :connection, :rejected]` fires.
- Start a server with `allowed_ips: [{127,0,0,1}]` and assert the normal greeting.
- Add unit tests for `{ip, port}` peers, bare-tuple peers and an unexpected format. Call `init/4` through a test-only wrapper or `:erlang.apply`.

### T-5 · MEDIUM · The global per-minute LMTP rate limit is never tested with a finite limit

- **Location:** `lib/custyard/email/lmtp_server.ex:1127`
- **Category:** untested-edge-branch
- **Consensus:** 3/3 verifiers

**Why it matters:**

- Three functions implement the ETS sliding-window limit shared across connections:
  - `check_global_limit/1` (lines 1127-1143)
  - `record_global_message/0` (line 1175)
  - `get_global_message_count/1` (line 1191)
- Every LMTP test that sends mail sets `messages_per_minute: :infinity` (test lines 963, 1000 and 1040).
- The only finite value (500, at line 935) is checked on `child_spec`, not enforced in a test.
- The following are therefore untested:
  - the `{:error, :global_limit}` path in `handle_DATA`
  - the rescue of `ArgumentError` when the ETS table is missing
  - window expiry and cleanup
- This limit is the server's only defense against a flood from an allowed MTA. An off-by-one error or a wrong ETS key shape would go unnoticed.

**Suggested fix:**

- Start a server with `rate_limit: [messages_per_connection: :infinity, messages_per_minute: 2, window_seconds: 60]`.
- Deliver two messages over separate connections, then assert that the third DATA gets the 4xx rate-limit response.
- Call `LMTPServer.cleanup_rate_limits(0)` and assert that the next message is accepted again.

### T-6 · MEDIUM · The signed webhook paths for Slack, Zendesk and Intercom are never tested through the controller

- **Location:** `lib/custyard_web/controllers/webhook_controller.ex:219`
