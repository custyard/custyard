The flow: you configure a Slack app's Events API to POST to custyard's `/api/webhook/route/:callback_token` endpoint. When a message is posted or an app mention occurs, Slack fires that webhook. The `WebhookController.routed/2` action looks up the inbound route by `callback_token`, finds `source: :slack` on the route record, and dispatches to `Custyard.Webhooks.Adapters.Slack`. That adapter verifies the request using Slack's signing protocol — HMAC-SHA256 over `v0:{timestamp}:{raw_body}`, checked against the `X-Slack-Signature` header — then normalizes the Slack event payload (user/bot ID, channel, message text, thread timestamp) into custyard's internal message format, and feeds it into the processing pipeline.

Slack's adapter has two notable differences from the others. First, signature verification requires the timestamp as part of the signed base string (`v0:{timestamp}:{body}`), so the simplified `verify_signature/3` callback always returns an error — only `verify_request/4` works. Second, the adapter handles Slack's URL verification handshake: when Slack sends a `url_verification` event during app setup, the adapter returns a `{:bypass, ...}` tuple so the controller can respond directly with the challenge string without dispatching into the processing pipeline.

Slack messages use channel + timestamp as identifiers (rather than email-style message IDs), and threading is based on `thread_ts` — if a message has a `thread_ts`, it's a reply in that thread.

The same `create_route/1` caveat applies: creating a Slack-sourced route still provisions a remote Lettermint mailbox and `callback_url/1` hardcodes `source=lettermint`. For Slack you wouldn't need a Lettermint mailbox; you'd just need the callback URL and the Slack app's signing secret.
