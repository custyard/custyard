The flow: you configure an Intercom webhook to POST to custyard's `/api/webhook/route/:callback_token` endpoint. When an Intercom conversation is created or replied to, Intercom fires that webhook. The `WebhookController.routed/2` action looks up the inbound route by `callback_token`, finds `source: :intercom` on the route record, and dispatches to `Custyard.Webhooks.Adapters.Intercom`. That adapter verifies the HMAC-SHA1 signature (via the `X-Hub-Signature` header), normalizes the Intercom conversation payload (author email/name, subject, body, conversation part IDs) into custyard's internal message format, and feeds it into the processing pipeline — creating or updating a conversation.

Intercom's adapter is more complex than Zendesk's because Intercom nests conversation data inside `data.item` with separate `conversation_parts`, and it needs to resolve the author from either the source or the latest conversation part. It also builds threaded `in_reply_to` references so that replies to an Intercom conversation thread into the same custyard conversation.

Note on HMAC-SHA1: Intercom's webhook signing uses SHA-1, not SHA-256. HMAC-SHA1 remains secure for message authentication (collision attacks don't translate to HMAC forgery), but SHA-1 is considered deprecated for new implementations. If Intercom introduces a SHA-256 signing option, the adapter should be updated.

The same `create_route/1` caveat applies here as with Zendesk: creating an Intercom-sourced route still provisions a remote Lettermint mailbox and `callback_url/1` hardcodes `source=lettermint` in the query string. For Intercom you wouldn't need a Lettermint mailbox; you'd just need the callback URL and a shared signing secret.
